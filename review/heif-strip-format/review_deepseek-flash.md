**1. Exif item: take C.** A leaves `infe` declaring `Exif` over zeros, so anything that trusts the declaration parses garbage (that is exactly Pillow's `SyntaxError`). D makes the declaration false the other way and requires inventing a fourcc; 23008-12 defines no null item type, so you are betting no reader ever assigns meaning to whatever you write. C keeps the declaration true.

Reader behaviour with C: libheif — unchanged, decodes, `heif_image_handle_get_metadata` returns an empty TIFF after the 4-byte prefix (sure). pillow-heif/Pillow — `getexif()` gets `MM\0*` and returns an empty Exif instead of raising (high confidence; it is the same code path that failed). Image I/O — already 0 keys; expect the same, at worst an empty `{Exif}` dict. Do **not** write Orientation 1: orientation 6 in your sample came from `irot`, not `Exif`, and an invented tag is a real risk of overriding it. ExifTool — no tags, no warning; an IFD0 with count 0 is legal, and `-validate` should be clean. Android/libheif, Chrome, Safari — same as libheif. WIC/Photos do not surface HEIC metadata.

**2. XMP.** Do not blanket-destroy. Personal data hides *inside* the packet (`exif:GPSLatitude`, `tiff:Model`, `xmp:CreateDate` in the `rdf:Description`), and your two packets are the only place I would expect non-personal XMP, so a denylist of property names is unsound. Rule: act only on `mime` items whose content type is XMP; keep a packet byte-for-byte only if it parses *and* every property resolves into an allowlist (`HDRGainMap:*`, `SemanticSegmentationMatte:*`, structural `x:xmpmeta`/`rdf:RDF`); otherwise replace with C. Fail closed. I do not know of a reader that consumes `HDRGainMap:HDRGainMapHeadroom` from XMP — the 21496-1 map carries its own headroom, and the JPEG lesson was EXIF maker notes, not XMP — so I rate the HDR risk as unproven, but the allowlist costs nothing and removing a matte's version property is a gratuitous change to portrait rendering. When unsure, C.

**3. Bytes.** Exif minimum is **18**: `00 00 00 00` (offset 0, TIFF starts at byte 4) + `4D 4D 00 2A 00 00 00 08` + `00 00` (entry count 0) + `00 00 00 00` (next IFD), then zeros to the original length. Offset 0 is self-consistent for offset-following readers and the `MM` scan finds it too; some writers use 6 plus `Exif\0\0` and readers accept both, but 0 cannot disagree with itself. Since the item cannot shrink, padding is free. XMP minimum ≈106: `<?xpacket begin='' id='W5M0MpCehiHzreSzNTczkc9d'?><x:xmpmeta xmlns:x='adobe:ns:meta/'></x:xmpmeta><?xpacket end='w'?>`, padded with spaces *before* the trailer (Part 3's prescription; ExifTool tolerates either). If an item is shorter than its minimum — impossible for a real Exif, conceivable for a tiny mime item — retype it (D) and zero what is left; do not write a truncated TIFF.

**4. B/D.** The trap in B: `meta` precedes `mdat`, so deleting `infe`/`iloc` entries shrinks `meta` and moves `mdat`, invalidating every absolute `iloc` offset. If you ever do it, keep `meta` the same total length by inserting a `free` box of exactly the removed bytes — then no offsets move and no box sizes above `meta` change. Then you must also fix `iinf`'s entry count, rebuild `iloc`'s variable-width records, remove the `cdsc` entry and decrement that `iref` box's count, drop the item from every `ipma` association (dangling ids make libheif mis-associate or error), and remove it from any `EntityToGroupBox` in `grpl` (its ids are explicit; a dangling id is a validation failure). D avoids all of that, and is the only option that works for `construction_method` 1 items inside `idat`, since the type sits in `infe` while the payload needs no rewrite — but you still cannot zero an `idat` payload without parsing `idat`, and a retyped item still holds the bytes.

**5. Invariants.** Output length equals input length; every byte outside the reported extents is identical (assert against a computed mask, not a hash). Picture items' extents unchanged and disjoint from wiped ranges; all non-metadata `iloc` records byte-identical. Each remaining `Exif` item parses as TIFF; each remaining XMP packet parses and yields zero non-allowlisted properties. No `GPS`, `Model`, `DateTimeOriginal` ASCII anywhere in the output, including unreferenced padding — a leak elsewhere in `mdat` is still a leak. `strip(strip(x)) == strip(x)` byte-for-byte. Pillow `getexif()` does not raise; ExifTool emits no `Warning:`/`-validate` output and reports no GPS/Model; Image I/O keeps orientation, ICC, HDR headroom and the gain-map auxiliary; libheif pixel hash identical.

**6. `strip_heif` itself.** `item_types` reads only `item_type`, so any `mime` item is destroyed regardless of content type — a `mime` item holding, say, an `image/png` thumbnail or `application/octet-stream` blob is wiped. The MIME type is in the `item_name` field of `infe` for `mime` items (verify on your sample), and the code never looks at it. The data reference index is read and discarded: with `dataReferenceIndex != 0` the extent lives in another file and those offsets mean nothing here — refuse. The overlap guard checks only `iinf`/`iloc`, not `iprp`/`ipco`/`idat` or the picture items' own extents, so a self-overlapping `iloc` could zero picture bytes. And `construction_method != 0` items are silently skipped, so an Exif item in `idat` survives while the run reports success — that must be a visible refusal, not silent incompleteness.
