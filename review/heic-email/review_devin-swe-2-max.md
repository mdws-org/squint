## Findings

**1. `imageio.rs:237-269` — row stride is assumed, never queried.** With `data = NULL`, Quartz allocates the backing store and chooses the real `bytesPerRow` itself; the value you pass is a request, not a guarantee. `CGBitmapContextGetBytesPerRow` exists precisely because the context may pad to its preferred alignment. You then do `from_raw_parts(data_ptr, w*h*4)` and `chunks_exact(4)`. If the actual stride exceeds `w*4`, the slice stays in-bounds, so this is silent: row 1 onward is shifted, the output JPEG is sheared diagonally, and `SQUINT_OK` is returned. Every tested width (1200, 2048, 5712) produces `w*4` divisible by 64, which is why it passed — feed it a 1001px-wide HEIC (`w*4 = 4004`, below Quartz's alignment quantum) and it will corrupt. Fix: add the `CGBitmapContextGetBytesPerRow` extern, iterate `stride`-spaced rows, drop 3 of 4 bytes per pixel.

**2. `imageio.rs:217-225` — RGB-model colorspace with no ICC produces an untagged JPEG.** `CGColorSpaceCopyICCData` returns `NULL` for colorspaces built from primaries (a `colr nclx` tag instead of `iCCP`) or calibrated spaces. Branch 1 then yields `icc: None`, and `encode_jpeg` writes Display P3 numbers into a file no profile describes — every reader assumes sRGB and the colours shift. That is invariant 2 violated silently. iPhone files carry `iCCP` so your measurements didn't catch it; a libheif/ffmpeg/Android-exported HEIC tagged nclx-P3 will. Fallback options: resolve `CGColorSpaceCopyName` and attach the matching profile, or refuse rather than ship untagged non-sRGB pixels.

**3. `lib.rs:652`, `heif.rs:231-234` — `signals_hdr` misses a whole class of HDR HEIC.** The two needles cover the Apple aux URN and the ISO 21496 aux URN, which is what iPhones write. But a single-image HDR HEIC signalled by `colr` nclx with a PQ or HLG transfer function carries no gain map and no aux URN at all — the needle scan finds nothing, `CGContextDrawImage` clamps the extended range into 8 bpc, and the result reports `Hdr::Absent` while HDR was destroyed. Invariant 4 broken for that class. Secondary miss: gain maps declared via XMP `hdrgm:` or vendor aux URNs that don't contain either needle. Over-reporting is impossible to get wrong (whole-file scan including `mdat` can only false-positive, which is the safe direction); under-reporting is the live risk. Cheap improvement: also parse `hvcC`/`colr` for non-SDR transfer functions, or document the miss class.

**4. `imageio.rs:199-258` — a corrupt bitstream produces a silent black JPEG.** `CGContextDrawImage` returns `void`. A HEIC whose headers parse but whose HEVC stream dies mid-decode leaves the context partially or fully zero-filled; there's no error path at this API level, so a black or half-decoded image encodes and ships as `name-email.jpg` with `SQUINT_OK`. Two cheap detections exist: call `CGImageSourceGetStatus` after `CGImageSourceCreateWithData` (catches truncated files at header level — `kCGImageStatusIncomplete`), and force the decode before drawing by copying `CGDataProviderCopyData(CGImageGetDataProvider(image))` and checking the result is non-null/full-length.

**5. `Preset.swift:37` — output extension is derived from the input filename, not the detected format.** A JPEG renamed `.heic` runs the email preset with `converted == false` and writes `photo-email.heic` containing JPEG bytes — a valid file with a wrong extension that Finder/UTI will misidentify. Symmetric wart at `JobQueue.swift:131-134`: a JPEG renamed `.heic` is refused by the pre-check even though it's a JPEG — fail-closed, so defensible, but the message ("use Shrink for Email") is wrong for a file that isn't a HEIC. The real guard is `converted`, which is byte-derived via `is_heif(bytes)` in `Source::open` — that's the correct design and it's what makes the post-check at `JobQueue.swift:143` trustworthy. The extension check is advisory; the naming could equally be derived from what the engine actually produced.

**6. `JobQueue.swift:151` — destination collision inside one batch.** `a.heic` and `a.jpg` selected together under the email preset both compute `a-email.jpg`; two `Task.detached` workers race an atomic write and last-finisher wins with no error. This class existed before (`.JPG` vs `.jpg`), but HEIC makes the realistic trigger common — same shoot, mixed formats, both selected in Finder. Minor but real.

**7. `lib.rs:660` — `NoSmallerResult` on a write-beside preset writes nothing and reports "already optimal".** A small or already-efficient HEIC whose q75 JPEG comes out ≥ source is refused, which honours invariant 3 — but the email preset's purpose is producing a JPEG copy, not shrinking. The user asked for a deliverable and gets "already optimal" with no file. Confirm this is intended rather than exempting the beside-write presets from never-grow.

**8. `imageio.rs:148-204` — multi-image HEICs silently take index 0.** `count` is queried and discarded beyond `>= 1`. Index 0 is the primary item, which is the right choice for burst covers and live-photo stills; an animated HEIF yields frame 0. Acceptable behaviour, but it's a silent decision — surface `count` on `Decoded` or at least note it.

**9. `source.rs:11` — Linux build hygiene.** `capped` and `MAX_PIXELS` are used only inside `#[cfg(target_os = "macos")]`, so non-macOS builds emit unused-import warnings; a `-D warnings` CI fails. `cargo metadata --locked` is unaffected (no new deps), `imageio`'s `#[link]` attributes never compile off-macOS, the test is `cfg`-gated, and the non-macOS arm correctly returns `ReadOnlyFormat`. Compiles on Linux with warnings.

**10. `main.rs:145` — stale `unreachable!("neither format can be re-encoded")`.** Only TIFF reaches it now. Cosmetic.

## Per-question verdicts

**1. Ownership is clean.** Every Create/Copy is wrapped in `Cf` exactly once: `cf_data` (142), `src` (145), `props` (153), `image` (199), `icc_data` (219), `dev_rgb` (227), `ctx` (240). Get-rule objects — `cs` (217), the dictionary values, `CFDataGetBytePtr` — are used strictly inside their owners' lifetimes; the ICC bytes are copied to a `Vec` inside `map` before `icc_data` drops (220-224). The `CGImageGetColorSpace` pointer is kept alive long enough for `CGBitmapContextCreate`: `ctx` is declared after `image` so it drops first, and the context retains its colorspace regardless. Early `?` returns unwind the guards in reverse order — no leak. Nits: `CFDataGetBytePtr` may return `NULL` on an empty CFData and `from_raw_parts(NULL, 0)` is UB-adjacent (223) — guard `len > 0`; `CFNumberGetValue` returns `Boolean` (u8), declared `bool` — works, should be `u8`; dictionary values are cast to `CFNumberRef` unchecked — ImageIO builds that dict so it's realistically always a number or absent, but a `CFGetTypeID` check is one line.

**2. Pixel order is R,G,B,X** for 8-bpc + `NoneSkipLast` + `ByteOrderDefault` on Apple silicon — your corner-pixel test would have caught BGRA or a flip. A same-size draw into a same-colorspace context is a pixel copy: no flip (row 0 of the buffer is image row 0 under Quartz's own convention — the canonical QA1509 pattern), no letterbox, no resample at 1:1. 16-bit/float sources clamp into 8 bpc — fine for the SDR base, silently lossy for PQ content (finding 3). Greyscale HEIC falls into the DeviceRGB branch: values get converted to ~sRGB untagged, acceptable. Multi-image and animated inputs yield the primary/first frame (finding 8).

**3. Bomb guard holds.** Declared dims checked at 195 before image creation; `CGImageSourceCreateImageAtIndex` is lazy, and actual dims from `CGImageGetWidth/Height` are re-checked at 209 before the 1 GB context — header/decoder disagreement cannot slip past. `w*h*4` is `checked_mul`'d (233). Remaining exposure: `MAX_DECODE_ALLOC` doesn't apply to ImageIO's internal decode, so a 250 MP 16-bpc source can still pull several GB inside the framework — parity with the existing risk, not a regression.

**4. `converted` is byte-derived** (`is_heif(bytes)` in `Source::open`, not the extension), so a HEIC named `.jpg`/`.png`/extensionless is caught by the `destination == url` post-check (143) even though the pre-check (131) only looks at extensions. `.HEIF` uppercase is handled by `lowercased()`. I found no path that writes JPEG bytes over a non-JPEG file; the residual issues are naming/refusal asymmetries (finding 5).

**5. Covered in finding 3** — needles cover Apple + ISO aux URNs; miss class is non-aux HDR (nclx PQ/HLG) and non-standard aux spellings. Whole-file scan can only over-report.

**6. JPEG/PNG path is a pure lift** — `Source::open`'s else branch is the same four calls in the same order; measurements show byte-identical JPEG output. The CLI prints strictly more than before (converted tag on the size line and on the result line); nothing it printed is gone. The TIFF early refusal is intact.

**7. Portable, with warnings** — see finding 9.
