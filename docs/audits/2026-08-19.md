## The five that matter

### 1. PNG loses its colour profile in Fast and Quality — VERIFIED

Measured on a Display P3 PNG:

| mode | profile out | bytes |
|---|---|---|
| source | Display P3 | — |
| fast | **none** | 124,373 |
| quality | **none** | 123,345 |
| strip | Display P3 | 155,664 |

`png::optimize_png` decodes to RGBA8 and re-encodes through the `image` crate's PNG encoder, which writes `IHDR`/`IDAT`/`IEND` and nothing else. Nothing on that path ever calls `extract_icc` or writes `iCCP`. `gAMA`, `sRGB` and `cHRM` go the same way.

This is the differentiator. The README's argument for the project's existence is that ImageOptim drops the profile and Squint does not — and for half the supported formats, in the two modes that re-encode, Squint drops it too. The original is overwritten, so it is not recoverable.

`core/src/png.rs:61-72`

### 2. A malformed-but-openable file becomes a truncated file, written over the original — VERIFIED

Both strippers return `Some(partial_output)` when their walk fails, instead of failing. `optimize` accepts it because a truncated file is always smaller than its source, and `Writer.replaceInPlace` then destroys the original.

I built a 398-file corpus of malformed JPEGs and ran all three modes over it — 1,194 invocations. No panics, no crashes, no hangs, which is a good result for the parsers themselves. But **7 files that macOS opens fine became files macOS cannot open**, all through Strip. Each was a JPEG with one wrong segment-length field: Apple's decoder resynchronises, Squint's walk desynchronises, breaks out, and returns the bytes accumulated so far as success.

`strip_png` has the identical shape and can return an 8-byte signature-only file.

Fix: return `None` unless the walk actually reached SOS/EOI (JPEG) or emitted IHDR+IDAT+IEND (PNG). Strip is the one path built entirely from hand-rolled byte surgery and the one path where nothing is ever decoded to check the result.

`core/src/metadata.rs:157,193,206`, `core/src/png.rs:200-215`, `core/src/lib.rs:418-425`

### 3. Files queued while a run is in progress are never processed — VERIFIED

`run()` snapshots the waiting list once. `add()` returns early whenever `isRunning`. When the run drains, nothing re-checks. Jobs appended mid-run sit at `waiting` forever.

The privacy consequence is the bad one: right-click 40 photos, then 10 more while the first batch runs. The 10 appear in the window, look queued, and are never touched. Their filenames are on screen, so they read as handled — and they still carry the client's address.

The class doc claims the opposite: "work arriving by either route joins the same run".

`app/Sources/JobQueue.swift:51-56, 63-71`

### 4. The app quantizes PNGs lossily by default; the CLI does not — REPORTED

`Engine.optimize(pngMinQuality: Int32 = 70)` is never overridden, so every PNG through the app is palette-quantized to 256 colours — in **Fast** mode, which computes no score, so nothing catches the damage. The CLI defaults to `None`, meaning lossless.

Every measurement in the README was taken with the CLI. They do not describe what the app does to a PNG.

`app/Sources/Engine.swift:49` vs `core/src/main.rs:44`

### 5. A gain map the extractor does not recognise is deleted and reported as absent — REPORTED

`GAIN_MAP_NEEDLES` matches Apple's two markers. A Google Ultra HDR JPEG signals its map differently. `extract` returns `None`, `strip_jpeg` cuts at EOI so the map is gone anyway, and the result reports `Hdr::Absent` — "the source carried no gain map."

The `Hdr` enum has three states and none of them means "a map was there and I could not read it." This is the precise failure the HDR work was done to prevent, one format over.

`core/src/gainmap.rs:34,132-138`, `core/src/lib.rs:406,476`

## Correctness

**The search's widening branch is dead code — VERIFIED by arithmetic.** `hi = predicted + 8`, and the up-widen fires only when `q >= hi - 0.5`, i.e. `round(predicted) >= predicted + 7.5`. Never true. The down-widen needs `round(predicted) <= predicted - 11.5`. Never true. The clamped edge cases are no-ops. So the search is permanently confined to `[predicted-12, predicted+8]`, and `Unreachable { best_score }` reports the best score *inside a window it never left* — a refusal presented as a measurement. Whether a real photograph falls outside the window is unverified. `core/src/lib.rs:282-291`

**Quality mode on PNG never consults the target — VERIFIED by reading.** `optimize_png` computes a score and returns it. There is no comparison, no search, no refusal. Set the slider to 90, get a file scoring 62, written in place, displayed as "score 62". The mode's contract holds for JPEG only. Also: when `min_quality` is `None` the candidate is a re-decode of the same bytes, so the reported score is ~100 by construction — a number measuring nothing. `core/src/png.rs:145-175`

**An imagequant failure reports a quality floor as a perceptual score.** `Error::Unreachable { best_score: min_quality as f64 }` puts a 0-100 imagequant setting into the field whose `Display` prints it as "best achievable score", a SSIMULACRA2 value. Surfaces in Fast mode, which has no target. `core/src/png.rs:101-103`

**The CLI bypasses the shared entry point for everything except Strip.** The doc comment on `optimize` says the harness and the C API both call it "so the application cannot drift away from what the CLI measures". Only Strip does. Drift already present: the CLI's fast path has no never-grow check, so it will write a file larger than its input where the app refuses. `core/src/main.rs:162-231`

**The search breaks instead of bisecting.** When interpolation lands on an already-probed quality it exits, leaving a bracket up to six points wide uncollapsed — the early exit the README says it avoids, reached by a different door. `core/src/lib.rs:261-262`

**Strip drops `cHRM`.** `PNG_KEEP` omits it, so a wide-gamut PNG carrying `gAMA`+`cHRM` and no `iCCP` keeps its gamma and loses its primaries — a colour shift, reported as "pixels untouched". `cICP`, `mDCV`, `cLLI` go too, so PNG HDR is dropped with no report at all. `core/src/png.rs:179-182`

**Strip destroys APNG animation.** `acTL`/`fcTL`/`fdAT` are not kept. Output is the first frame, smaller, reported as success. `core/src/png.rs:191-215`

**Two `run()` loops can be live at once.** `isRunning` is set inside `run()`, which is enqueued rather than executed synchronously, and `ContentView.load` calls `add` once per dropped file. Two adds landing before the first run body starts both spawn runs over overlapping snapshots — the same file optimized and replaced twice, concurrently, at double the memory limit. `app/Sources/JobQueue.swift:54-55`

**The Finder service rewrites the window's mode.** `JobQueue.shared.mode = mode` mutates the property the picker is bound to, with no guard during a run. Combined with the orphaned-jobs bug, a file right-clicked as Strip can later be processed as Fast. `app/Sources/ServiceProvider.swift:56`

## Robustness

**No decode limits anywhere.** `image::load_from_memory` runs with `Limits::default()` — no dimension cap, no allocation cap. A 40 KB PNG declaring 60000×60000 asks for 14.4 GB, and Fast/Strip run one job per core. Either an abort that kills every in-flight job, or a swap storm. There is no per-job timeout and `clear()` is disabled while running, so there is no way out. `core/src/lib.rs:76-82`, `core/src/png.rs:21-32`

**Only `encode_jpeg` is inside `catch_unwind`.** Any panic elsewhere — `image`, `imagequant`, `oxipng` — unwinds into an `extern "C"` frame and aborts the process. The typed-error contract cannot hold while the outermost frame has no guard. `core/src/ffi.rs:74-117`

**The MPF entry scan is quadratic in a crafted file.** Entry count is bounded only by the 64 KB segment, and `extract` substring-searches a file-sized slice per entry. ~4,095 entries against a 20 MB JPEG is on the order of 10¹¹ byte comparisons, single-threaded, no timeout. `core/src/gainmap.rs:113-138`

**No `Cargo.lock` committed — VERIFIED.** `core/` has none, and the Xcode pre-build step runs `cargo build --release`, so every build resolves fresh versions of a tree that includes build scripts compiling C. For a GPL-3 project distributing binaries, the corresponding source of any given build is also unpinned.

## Usability

**Invoked from Finder with the window closed, nothing is visible.** The app deliberately outlives its window so the service keeps working. The service then calls `NSApp.activate`, which brings forward an app with no window. The code comment says "Bring the window forward so progress is visible"; the call does not do that. Files are rewritten with no progress, no result, no score, no error. `app/Sources/ServiceProvider.swift:52-58`

**Every error message drops the number that would let you act.** `Error`'s `Display` builds real sentences — "best achievable score was 88.20", "requires at least 113px" — and none of them cross the FFI, which passes an integer mapped to a fixed string. So "the quality target cannot be reached for this image" arrives without the one fact that tells you to lower the slider to 88.

And none of the six messages says **the file was not changed**. In a tool that overwrites in place with no undo, that is the single most valuable clause and it is missing everywhere.

**Strip answers the wrong question.** The result line reads `1.4 MB to 1.4 MB, 2% smaller`. The question that was asked — is the location data gone — is never answered. Suggested: `location and camera data removed, HDR kept`.

**A Strip no-op reads as success.** No shrink returns `NoSmallerResult`, which the app renders as "already optimal". Nothing was written. For a file with nothing to remove that is fine; the word "optimal" reads as "clean", which is a different claim.

**The Services entries vanish with no explanation** on a folder, a mixed selection, or a HEIC — the default iPhone format. The menu simply has no Squint in it, which reads as a broken install. Nothing documents the rule.

**The menu titles are all the user gets.** `NSServiceDescription` is never rendered by macOS. "Squint (Fast)" / "(Quality)" / "(Strip Metadata)" tell you nothing about in-place overwriting or which one removes location data, and "Fast vs Quality" is exactly the decision-at-point-of-use the project says it avoids. Consider naming by outcome: *Shrink for Email*, *Shrink to Quality Target*, *Remove Location Data*. Note Services sort alphabetically by title, so the title is also the sort key.

**The install section does not end with a working app.** No `-derivedDataPath`, so the reader never learns where the app went, that it belongs in /Applications, or that the Finder entries do not appear until it has been launched once. No Gatekeeper note, and since Sequoia Control-click no longer bypasses it. No macOS version minimum. `ENABLE_HARDENED_RUNTIME: YES` next to `CODE_SIGNING_ALLOWED: NO` is inert and will read as already-configured when notarization is set up.

**Strip removes the capture date** and the README never names it. For job documentation that is the field that matters, and it is unrecoverable.

**The differentiator is invisible in the UI.** Colour profile preservation appears nowhere on screen. The score only exists in Quality mode, and Fast is the default — so the headline feature is absent from the default path, and when it does appear it reads "score 76.9" against no scale.

## Clean

- **Bounds safety of the hand-written parsers.** Every slice and index in `gainmap.rs`, `metadata.rs` and `png.rs` traced against attacker-controlled offsets: no reachable slice panic, no usize underflow, no loop that fails to advance. Corroborated by the corpus run — 1,194 invocations over deliberately hostile MPF offsets, sizes, counts and truncations produced **zero panics, zero crashes, zero hangs**, and every rejection was a typed error.
- **FFI ownership and layout.** 40 bytes on both sides, matching field order including the new `hdr` field, freed exactly once on every path including errors, copy before free, unknown enum values handled. One contract nit: `from_raw_parts(ptr, len, len)` assumes `shrink_to_fit` yields exact capacity, which is not guaranteed — benign on the current allocator, UB by the letter.
- **`Writer.replaceInPlace`.** Same-directory atomic temp, `replaceItemAt` with no options so Finder tags and creation date survive, temp cleaned up on throw. A full disk, a read-only file or a crash mid-write all leave the original intact. (A selected symlink is replaced by a regular file, and a crash between write and replace leaves a `.squint-*.tmp` behind.)
- **`oriented()`** — all eight EXIF transforms verified by hand.
- **Mode dispatch** now agrees across all four surfaces, and `ffi.rs` names every mode rather than defaulting the unknown case into Strip.
- **Licensing.** `GPL-3.0-or-later` in `Cargo.toml`, GPLv3 in `LICENSE`, correct and required given libimagequant. No dependency licence conflicts. Missing: per-file notices and a third-party notice file in the distributed app.
- **The HDR work from PR #13** holds up: preserved in Strip, reported in every mode, in both the app and the CLI.

## Suggested order

1. PNG colour profile (#1) and the truncation-as-success bug (#2). Both silently destroy originals, both are small fixes, and both contradict the project's own stated rules.
2. The queue bugs (#3, plus the double-run race). One restructure fixes the orphaned jobs, the race, and the mode capture together.
3. The PNG lossy-by-default divergence (#4), because until it is settled no PNG measurement means anything.
4. Decode limits and a `catch_unwind` at the FFI boundary. Cheap, and they convert two whole-app failures into typed errors.
5. Commit a `Cargo.lock`.
6. The usability set, which is mostly wording and one window-opening call.
