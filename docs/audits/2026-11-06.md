# Squint audit, 2026-11-06

An outside review of `main` at `b00f944` (0.9.8 plus two maintenance commits), made in one read-only pass on 2026-11-06. It reported ten findings, each with a file and line, a scenario and a proposed fix. None of them had been reproduced when they were reported.

Every claim was checked on 2026-11-07 by building the engine at `b00f944` on svk (macOS 27.2, release build) and running a repro file through the `squint` command line. `tools/audit-2026-11-06.py make` writes the repro files, from `sips` and ExifTool output wherever those tools can write the shape, and `judge` checks the engine's output with tools that are not squint: `exiftool -a -G1 -u`, Image I/O through `tools/imageio-probe.swift` (the orientation it reads and the size it draws the picture at), and a byte scan of the output with every Flate stream of a PDF inflated. Against `b00f944` it reports 21 checks that find a defect; against the fixed branch, none.

Each confirmed finding has a regression test, and each test was run against the unfixed code before the fix and failed. Where a test needs a function the fix adds, it was also run with the fix's check planted to never fire, and failed. The fixes are on branch `audit-2026-11-06`, one commit per finding. They are not merged or released.

### 1. GIF graphic control and plain text extensions: CONFIRMED

The claim: `gif.rs` copied a Graphic Control Extension (`0xF9`) and a Plain Text Extension (`0x01`) whole, so sub-blocks after a graphic control's four bytes, and plain text past the end of its grid, passed through Strip. The two kept application extensions were already checked by their content, and these two were kept by label alone.

Repro: `f1-gce.gif` is a `sips` GIF with a comment and a graphic control whose four-byte sub-block is followed by a second one holding `uid=jdoe GPS 51.5007,-0.1246`. `f1-plaintext.gif` has the same comment and a plain text extension whose grid holds one 8x8 cell, followed by the same 28 characters.

Result at `b00f944`: Strip removed the comment, reported metadata removed, and the planted text was in both outputs. Image I/O draws both at 16x12 either way.

Fix: the graphic control is rebuilt from its four-byte sub-block and refused when the first sub-block has another length. The plain text extension keeps its twelve-byte header and as many characters as its grid has cells, and is refused when the header has another length or a cell has no size. After: the text is in neither output.

### 2. WebP and PNG orientation: CONFIRMED

The claim: Strip dropped a WebP's `EXIF` chunk and a PNG's `eXIf` chunk whole, orientation included, while copying the pixels unchanged. The JPEG path writes the orientation back, and these did not. The comment in `webp.rs` saying the turn "has already been applied to the pixels by then" is true only of the re-encode paths.

Repro: `f2-orient6.webp` (a lossless WebP) and `f2-orient6.png`, each given `-n -Orientation=6` by ExifTool 13.55. Image I/O reads orientation 6 and draws both at 12x16. The same two files, from that run, are `core/tests/fixtures/orientation-6.webp` and `orientation-6.png`.

Result at `b00f944`: Image I/O drew both Strip outputs at 16x12, on their side. Fast on the PNG, lossless and quantized, did the same, which the audit did not name: the PNG re-encode decoded without applying the tag and wrote no `eXIf`.

Fix: Strip reads the orientation first and writes it back in a chunk holding only that tag, the block JPEG Strip already wrote. The WebP keeps its `VP8X` EXIF flag when it does. The PNG re-encode applies the turn to the pixels. After: every output is drawn at 12x16, and ExifTool shows Orientation and no other EXIF tag in the stripped files.

### 3. HEIF metadata boxes and item names: CONFIRMED

The claim: `free_metadata_boxes` freed top-level `uuid` boxes and boxes inside `moov`, but not `xml `, `bxml`, `keys` or `ilst` inside the file-level `meta`, and nothing cleared the name each `infe` entry carries.

Repro: three files made from a `sips` HEIC, each with one shape inserted and every enclosing box size and `iloc` offset moved to match: `f3-xml.heic` (an `xml ` box of XMP), `f3-keys.heic` (`keys` and `ilst` naming an author) and `f3-name.heic` (the picture item named `IMG_0042.HEIC`). Image I/O draws all three. ExifTool `-a -G1 -u` shows the XMP as `XML-dc:Description` and the author as `Keys:Author`; it does not show item names, so those were checked in the bytes.

Result at `b00f944`: Strip answered "nothing to remove; the file was not changed" for all three, which is a claim the file is clean.

Fix: those four box kinds and `udta` inside `meta` become `free` boxes of the same size, and every item name is cleared. The strings after a name (a `mime` item's content type and encoding) move up behind an empty name and the bytes left over are zeroed, so no offset changes. After: ExifTool shows neither tag, the name is absent from the bytes, and Image I/O draws all three outputs at 16x12. A `sips` HEIC given a GPS position, a camera make and an XMP creator by ExifTool still strips, with none of the three left, and Image I/O draws it.

### 4. PDF JavaScript and unreached annotations: CONFIRMED

The claim: nothing removed document JavaScript (the `/Names /JavaScript` tree, `/OpenAction`, `/AA`), and the annotation scrub read only annotations listed in an `/Annots` array, so one reached through the AcroForm's `/Fields`, a field's `/Kids` or a reply's `/IRT` kept its author and dates.

Repro: `f4-scripts.pdf`, written by the script, carries a script in the name tree that sets the document author, one in `/OpenAction`, one in the catalog's `/AA` held in a stream, and one in a page's `/AA`. It also has a form field whose only widget is its kid, and a comment replying to another comment that no `/Annots` lists. The planted author is `Jane Doe` and the planted date `D:20260101120000`.

Result at `b00f944`, scanning the Strip output with its object streams inflated: `/JS` 4 times, `/JavaScript` 5, `/OpenAction` 1, `/AA` 2, the author 3 and the date 4.

Fix: every entry whose value is a JavaScript action is removed wherever it sits, the `/JavaScript` tree goes whole, an `/AA` or `/Next` left empty goes, and the action objects, their script streams and the tree's nodes are deleted. This runs in every mode. The annotation scrub now also follows `/Fields`, `/Kids`, `/IRT` and `/Popup`; what is reached as a field keeps its `/T`, which is the field's name. The number of scripts removed reaches the CLI line and the app's row ("4 scripts removed"). After, in both Strip and Fast output: none of the six strings, the field name kept, and Quartz opens the file at one page.

### 5. Quality search memory: CONFIRMED

The claim: `MAX_PIXELS` bounds the decode at 250 megapixels, but nothing bounds the search, which holds the picture, each candidate and the metric's working planes at once.

Repro: `tools/audit-2026-11-06.py measure`, noise JPEGs through the release build, peak resident memory from `/usr/bin/time -l`:

| picture | Fast | Quality | Quality per pixel |
|---|---|---|---|
| 1.5 MP | 0.038 GB | 0.491 GB | 328 B |
| 3 MP | 0.073 GB | 0.964 GB | 321 B |
| 6 MP | 0.133 GB | 1.650 GB | 275 B |
| 12 MP | 0.262 GB | 3.158 GB | 263 B |

The peak grows with the pixel count across an eightfold range, at 263 to 328 bytes a pixel. A picture at the decode limit was not run: at 263 bytes a pixel it would ask for about 66 GB, and svk has 8 GB.

Fix: `max_quality_pixels()` is the pixel count whose search fits in half of the Mac's installed memory (`hw.memsize`), at a measured 300 bytes a pixel (peak footprint 1.64 GB at 6 MP and 3.56 GB at 12 MP on an 8 GB M1, rounded up): about 14 MP on 8 GB, 28 MP on 16 GB and 57 MP on 32 GB, so a 12 MP phone photograph stays searchable on the smallest supported Mac. Above it, Quality encodes once at the fixed quality, as Fast does, on the JPEG path, the HDR path, the PNG colour search and each picture inside a PDF, and the result says so on the CLI line and in the app's row. A solid 8250x6200 (51.15 MP) JPEG in quality mode on the 8 GB Mac now peaks at 0.83 GB. The audit's proposed fixed 50 MP cap was not used: at the measured cost a 50 MP search peaks near 15 GB.

### 6. An orientation typed LONG: CONFIRMED, with a different consequence

The claim: `orientation_in_tiff` read the orientation's value as a SHORT whatever the field's type, so a big-endian LONG 6 read as 0. The audit expected the source to display turned and the output not.

Repro: `f6-long.jpg` and `f6-long-ii.jpg`, a `sips` JPEG with an EXIF block whose only field is Orientation typed LONG with value 6, in big-endian and little-endian order. ExifTool reads both as "Rotate 90 CW". Image I/O reports no orientation for either and draws both unturned at 16x12.

Result at `b00f944`: for the big-endian file, Strip wrote an Orientation of 0, which ExifTool shows as 0 and no reader accepts; the picture was not turned either way, so the display claim did not reproduce on macOS. For the little-endian file the misread came out as 6, and Image I/O drew the Strip and Fast outputs at 12x16, turned where the source was not.

Fix: an orientation is read only as Image I/O reads it, a SHORT from 1 to 8, and anything else is no orientation. After: all four outputs are drawn at 16x12 and carry no Orientation tag. A viewer that reads the LONG as ExifTool does will draw these sources turned and the outputs not. Viewers other than Image I/O were not checked.

### 7. Text inside an ICC profile: WON'T FIX

The claim: Strip keeps every colour profile verbatim, and a profile's `desc`, `cprt`, `mluc` and `text` tags are free text that could name a device or a person.

Checked: a `sips` JPEG with the Display P3 profile keeps `ProfileDescription: Display P3` and `ProfileCopyright: Copyright Apple Inc., 2022` through Strip.

This is left as it is: the project's rule is that the colour profile is never stripped or altered, in any mode, and editing a profile's tags in place is an alteration.

### 8. Multi Picture Format types: CONFIRMED

The claim: `gainmap::attach` wrote every secondary with attribute 0 (undefined) and the primary as a plain baseline primary, whatever the source's index said.

Repro: `f8-stereo.jpg`, two `sips` JPEGs joined by an index listing both as disparity images (`0x020002`), the first flagged as the picture to show. ExifTool reads MPImageType "Multi-frame Disparity" for both.

Result at `b00f944`: after Strip, ExifTool read "Baseline MP Primary Image" and "Undefined", and the representative flag was gone.

Fix: every entry's attribute word and dependent entry numbers are read with the pictures and written back with them. After: "Multi-frame Disparity" for both and the representative flag on the first. An iPhone HDR photograph lists "Baseline MP Primary Image" and "Undefined" before and after, and Image I/O still finds its Apple and ISO gain maps.

### 9. `%PDF-` in a picture: CONFIRMED

The claim: `is_pdf` accepts the marker anywhere in the first 1024 bytes, so a picture holding it there is sent to the PDF rewriter. It fails closed.

Repro: `f9-comment.jpg`, a `sips` JPEG given `-Comment=%PDF-1.7 scanned by Jane Doe` by ExifTool.

Result at `b00f944`: Strip exited 1 with "this PDF could not be read: failed parsing cross reference table".

Fix: the window stays, because some PDFs put bytes before the marker, but a file that opens as a JPEG, PNG, GIF, WebP, HEIF or AVIF, TIFF or SVG is not a PDF. After: Strip succeeds, ExifTool finds no Comment, and Image I/O draws the output.

### 10. A file edited while it is processed: CONFIRMED through the CLI

The claim: `JobQueue.process` reads a file, optimizes it and replaces it with no check that the file is unchanged, so an edit saved during a long job is overwritten by a result made from the old bytes.

Repro: the app was not run. The CLI has the same read, optimize, write sequence when `--out` names the input. `judge` starts a quality run on `f10-race.jpg`, a 3000x2000 noise JPEG, writes another file's bytes over it 1.5 seconds in, and compares the file afterwards.

Result at `b00f944`: the CLI's result replaced the edit.

Fix: the app stamps the file (size, modification date, file number) before reading it and compares the stamp before replacing it in place, failing the row with "the file changed while Squint was working on it, so nothing was written". The CLI compares size and modification time and exits 1. After: the edit survives. The app change was compiled in an `xcodebuild` Debug build of the Squint scheme and was not exercised.
